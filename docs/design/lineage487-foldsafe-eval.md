## 0. 要点
- いまの v3 の評価は縮小版（LB 0.282）しか回せない。その上での勝ちは LB に移らなかった（ランカー 0.246）[確認: #37、#3]。0.487 系統そのものを v3 で回すには、全 train で学習した部品を、v3（fold 0）を見ていない版に替える必要がある
- 段階を 3 つに分ける
  - **Tier 0**: 学習しない。既にある fold-safe のモデルと自前の表に差し替えるだけ。ただし学習済みのまま残る部品（Engine 1 ランカー `ranker_v4b`、fe_v4 の fragnet、ICEBERG/GLACIER）の漏れを数えて記録する
  - **Tier 1**: 公開の学習コードで、fold 0 と v3 の正解を外して学習し直す（Engine 1 ランカー、fragnet、v80、別の FPNet 1 本）
  - **Tier 2**: 重いもの（fe_D DreaMS の微調整、FPNet A/B、ICEBERG/GLACIER）
- 回す場所は Kaggle。0.487 写しを生成スクリプトで書き換え、ホールドアウトを test として渡す（`references/holdout-pipeline-eval.md` の手順）。手元の Mac では回せない（GPU の段と全 train の読み込みがあり、空きメモリは約 6 GB）
- GPU の重い段を出し終えたところで、候補ごとの表を書き出す。後段は手元の CPU でやり直す（再生）。この形にすると、自前の部品の多くは手元で何度も測れる
- **信じる前に較正を通す**（§5）。既知の LB の差のうち大きい 2 つ（Engine 2 off −0.101、縮小版 −0.197）が、v3 の評価でも区間ごと同じ向きに出ることを条件にする
- 検出力（§6）
  - 1 集合（200 分子）で検出できる差（対応のある差、80%・両側 5%）は 0.025〜0.053 で、Public（約 125 分子）の 1.26 倍しか鋭くない
  - 4 集合を合わせると（795 分子）0.012〜0.027 で、Public の約 2.5 倍鋭い
  - +0.01 を検出するには約 3,100 分子が要る
- 最初の到達点（§7、約 2 日）: 漏れの監査のスクリプト、生成スクリプト、v3 のデータセットを作る。そのうえで、Tier 0 の系統（または Engine 2 off の版）を v3_c1+enveda_v1 で 1 回だけ回し、版ごとの MRR を出す

## 3. どこで回すか（d）

### 3.1 Kaggle で回す（主案）
- 生成スクリプト `scripts/cv/make_lineage_fs_kernel.py`（未作成）が、`kernels/lb487`（c3d9992）からノートを作る。手では書き換えない。中身は 4 つ

  2. `FROZEN_B64` を復号し、§2 の差し替えを入れる。入れる先は F c37（FP バンクと model_views）、F c34（PubChem バンク）、F c32（Engine 2 の表のパス・`blk_base_fs`・`zlog_fs`）、窓のパッチ。どの置き換えも「ちょうど 1 回当たる」ことを assert する。入れ子の文字列リテラルの中は、リテラルと同じ書き方でエスケープする。最後に再エンコードし、`FROZEN_SHA256` を書き換える
  3. 外側のセル 15 の `_swap_to_ours` を #54 の重みに向ける
  4. 全セルと入れ子のモジュールを `compile()` してから出力する
- 読み込みの監視: `torch.load`・`lgb.Booster`・`np.load`・`pickle.load` を包む。禁止の名前を読み込んだら例外にし、読んだファイルを全部 `opened_files.json` に書く。受け入れ条件は `opened_forbidden == []`

### 3.2 手元での再生（GPU を何度も使わないため）
- GPU の段（Engine 1/2、PubChem、ICEBERG/GLACIER、神経スコアラー）が終わった所で、分子 × 候補ごとの表を parquet に書き出す
  - 中身は、各エンジンのリスト・生の点・ICE/GL の生の点・sanpier の点・lib_max・prior

## 6. 検出力（v3 と Public LB の比較）

既存の出力から計算した [計算]。計算は `outputs/local_eval/<set>/submission_*.csv` と `outputs/holdouts/<set>/truth.csv` に `scripts/validate/mrr25.py` を当てたもの。

| 集合 | n | MRR（score+prior+frag） | 分子ごとの RR の標準偏差 | 対応のある差の標準偏差（frag あり／なし） | 同（pmi 段あり／なし） |
|---|---:|---:|---:|---:|---:|
| v3_c1 | 200 | 0.8535 | 0.268 | 0.125（25 分子が動く） | 0.219（40） |
| v3_c2 | 200 | 0.0117 | 0.102 | 0.000（0） | 0.047（1） |
| enveda_v1 | 200 | 0.8376 | 0.300 | 0.140（20） | 0.203（37） |
| v3_c2n | 195 | 0.6284 | 0.408 | 0.203（51） | 0.268（78） |

- 検出できる最小の差（MDE、対応のある差、両側 5%・検出力 80%）は 2.80 × sd_d / √n
  - 1 集合（n = 200）: sd_d = 0.125 → **0.025**、0.20 → **0.040**、0.27 → **0.053**
  - 4 集合を合わせると（n ≈ 795）: 0.125 → **0.012**、0.20 → **0.020**、0.27 → **0.027**
  - +0.01 を 80% で検出するには、sd_d = 0.2 のとき n ≈ (2.8 × 0.2 / 0.01)² ≈ **3,100 分子**
- Public LB（約 125 分子）
  - 1 本の値の SE は 0.45 / √125 ≈ **0.040**。逆数順位の標準偏差約 0.45 は #3 の記録 [確認: engine2-rebuild.md §6]
  - 2 本の提出の差は同じ分子の上での対応のある差なので、SE は sd_d / √125。sd_d は隠れテストでは分からない。v3 の 0.2 を当てはめると 0.018、MDE は **0.050** [計算、sd_d は仮定]
  - いまの帯（SE 0.035〜0.04）は、差の読み方としては約 2 倍控えめ。それでも +0.01〜0.02 は見えない
- まとめ
  - 1 集合（200）は Public より √(200/125) = 1.26 倍しか鋭くない
  - 4 集合を合わせて約 2.5 倍
  - 効きが +0.01 の部品は、4 集合を合わせても検出力が約 30% しかない [計算: z = 0.01 / (0.2/√795) ≈ 1.41 → 検出力 ≈ 0.29]
  - 利点は鋭さだけではない: 分子ごとの差と区間が見える、提出の枠を使わない、Public に寄せる過学習が無い
- 大きくする案（Tier 1 と同時期、別 Issue）
  - fold 0 から 4 集合を各 600〜800 分子に増やす「v4」。Kaggle の時間は分子数にほぼ比例するので、1 版あたり約 12〜16 GPU 時間 [未確認、線形の仮定]。手元の再生（§3.2）と組み合わせないと回らない
  - timsTOF の構造が fold 0 にどれだけあるかが上限になる。数は未確認
